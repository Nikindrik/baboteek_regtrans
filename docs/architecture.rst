Архитектура и поток данных
==========================

Общая схема
-----------

::

   NDTP emulator
       |
       | TCP :9201
       v
   Backend (Go)
       |-- NDTP framing / CRC / Nav00
       |-- unit_id -> tr_id
       |-- schedule matching
       |-- strict target (T+10m, T+15m]
       |-- current deviation / diagnostics
       |
       | gRPC :50051
       v
   ML runtime (Go + ONNX Runtime)
       |-- rolling telemetry state
       |-- frozen 96-feature builder
       |-- residual delay regression
       |-- late-risk classification
       v
   Backend fleet state
       |-- REST
       |-- WebSocket
       |-- incidents / What-if
       v
   React dashboard via nginx :8088

Backend
-------

Backend принимает бинарные NDTP-пакеты, валидирует framing и CRC, декодирует
Nav00, сопоставляет ``unit_id`` с рейсом ``tr_id`` и вычисляет текущее состояние
относительно расписания. Только после определения валидной цели в строгом
горизонте запрос на прогноз передается в ML-сервис.

ML-runtime
----------

ML-сервис хранит причинную историю телеметрии по рейсам, строит фиксированный
вектор из 96 признаков и выполняет два ONNX-инференса: регрессию будущего
отклонения и классификацию риска опоздания. История, созданная при offline
валидации, не переносится в live gRPC-сессию.

Frontend
--------

Frontend получает агрегированное состояние только от Backend. Он показывает
позиции ТС, текущие и прогнозные отклонения, риск, инциденты и What-if сценарии.
ТС без расписания остаются видимыми в статусе «Мониторинг» и не окрашиваются как
риск только из-за отсутствия прогноза.

Отказоустойчивость
------------------

* Неизвестное или не имеющее расписания ТС не приводит к ошибке всего потока.
* Старый прогноз инвалидируется при исчезновении или смене target stop.
* Запоздавший ответ ML для старой цели не перезаписывает новую цель.
* Backend может явно помечать резервный heuristic fallback, не маскируя его под ML.
* What-if не изменяет live-состояние и не переписывает ML-прогноз.
